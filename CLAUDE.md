# Legacy Lacrosse Training

Marketing + booking site for a personalized lacrosse goalie training business
serving Ann Arbor, Ypsilanti, and Metro Detroit.

## Stack

- Next.js (App Router) + TypeScript + Tailwind CSS v4
- Cal.com for booking/availability (embedded, not custom-built)
- Resend for transactional email
- Vercel for deployment
- Playwright for e2e testing

Supabase, Stripe, and a custom database are **not** part of the MVP. Add them
only when a concrete feature needs persistent app-owned data (e.g. lead CRM,
session history, payment records) — see the engineering principle below.

## Engineering principle

Prefer boring, managed functionality over custom infrastructure unless custom
behavior materially improves the customer experience or the business. This is
a small coaching business site, not an enterprise app — resist premature
abstraction and unnecessary dependencies. Introduce an abstraction (a shared
component, a config file, a helper) only when it solves a concrete reuse or
correctness problem that already exists in the code — not for a hypothetical
future need.

## Architecture notes

- No route groups (`(marketing)` etc.) — nearly the whole site is marketing
  content, so a flat `app/` structure is clearer.
- `lib/site-config.ts` is the single source of truth for brand copy, nav
  links, and service-area data. `lib/services.ts` is the single source of
  truth for training offerings (name, format, description) — it backs the
  homepage summary today and will back the future Training page and booking
  flow. Never hard-code prices or offering details in components.
- Reusable UI primitives live in `components/ui/` (`Button`, `PlaceholderImage`).
  Don't add generic wrapper components (Card/Container/etc.) unless there's
  real duplication to justify them.
- `components/Header.tsx` is a client component (mobile nav state, current-page
  indicator via `usePathname`, Escape-to-close, resize handling).
  `components/Footer.tsx` is a server component.
- `Button` (`components/ui/Button.tsx`) is a discriminated union: passing
  `href` renders a `next/link`, omitting it renders a native `<button>` typed
  `type="button"` by default. Don't reintroduce a shared anchor/button prop
  intersection with casts — extend the union instead.
- The homepage hides its Testimonials section entirely when there are no
  real testimonials (`app/page.tsx`'s `testimonials` array) — never ship an
  empty section explaining that testimonials are "coming soon."
- `app/layout.tsx` has a skip-to-content link targeting `#main-content`; the
  `<main>` it points to is `tabIndex={-1}` so it can actually receive focus
  when the link is activated (an anchor target isn't focusable by default).
  Covered by the skip-link test in `e2e/homepage.spec.ts` — don't remove the
  `tabIndex` or the assertion without replacing the mechanism it protects.

## Design system

- **Colors** (see `app/globals.css` `@theme`): `ink` / `ink-2` (near-black
  navy, dominant dark surfaces), `paper` / `paper-2` (warm off-white, primary
  background), `accent` / `accent-deep` (brass/gold — reserved for booking
  CTAs and key brand marks, not decorative use). `ink-muted` / `paper-muted`
  are solid, WCAG AA-passing colors for secondary/caption text — use them
  instead of low-opacity (`text-ink/40`, `text-paper/45`, etc.) text, which
  can silently fail contrast requirements. Opacity modifiers on `ink`/`paper`
  text are fine only when you've checked the resulting contrast is ≥ 4.5:1
  (normal text) or ≥ 3:1 (large text, 24px+/19px+ bold).
- Colors live directly in `@theme` (not `:root` + a self-referential
  `@theme inline`). Only put a variable in `@theme inline` when it must
  reference a differently-named CSS variable at runtime — e.g. the
  `next/font` variables (`--font-fraunces`, `--font-inter`), which don't
  exist until the font loader injects them.
- **Type**: `font-display` (Fraunces, serif) for headlines, `font-sans`
  (Inter) for body/UI text.
- **Visual direction**: premium collegiate athletic brand — confident,
  editorial, generous whitespace. Avoid rounded "cards," pill buttons,
  gradients, icon grids, and generic SaaS landing-page conventions.
- Primary conversion action is always "Book Training" — the accent color is
  reserved for that action so it stays visually distinct everywhere.

## Coding expectations

- TypeScript strict mode is on (`tsconfig.json`) — don't weaken it, and don't
  use `any`/casts to route around a type error; fix the type.
- Route-aware types like `LayoutProps<"/">` (used in `app/layout.tsx`) are
  generated by Next, not hand-written — keep using them rather than reverting
  to manual prop types. `npm run typecheck` runs `next typegen` first for
  exactly this reason; don't replace it with a bare `tsc --noEmit` (in CI or
  locally) or type checking will fail on a clean checkout before those types
  exist.
- Default to no comments. Only add one when the *why* is non-obvious (a
  hidden constraint, a workaround, something that would surprise a reader) —
  not to restate what the code already says.
- Run `npm run lint` and `npm run typecheck` before considering a change
  done; fix failures rather than suppressing rules or adding `// @ts-ignore`.
- Match existing patterns (server components by default, `"use client"` only
  where state/effects/browser APIs are needed) rather than introducing a new
  pattern for one component.
- Accessibility is a requirement, not a nice-to-have, given this is a public
  marketing/booking site: real semantic HTML, visible focus states,
  keyboard-operable interactive elements, `aria-current` for nav state, and
  checked color contrast (see Design system above).

## Security rules

- Never commit secrets. API keys (Cal.com, Resend, etc.) go in an untracked
  `.env.local`; `.gitignore` already excludes `.env*`.
- Only prefix a variable `NEXT_PUBLIC_` if it truly must be readable in the
  browser — everything else stays server-only.
- Validate and sanitize any user input at the boundary once forms/booking
  land (contact form, booking flow) — don't trust client-supplied data in
  API routes or server actions.
- Don't use `dangerouslySetInnerHTML` unless the content is sanitized and the
  source is trusted; prefer plain JSX.
- Keep dependencies minimal and current; avoid adding a package for
  something a few lines of code or an existing dependency already covers.

## Assets needed from the business owner

The site currently uses labeled placeholder blocks (`components/ui/PlaceholderImage.tsx`)
wherever real photography is required. Drop finished files into
`public/images/` and swap the corresponding `PlaceholderImage` for a
`next/image` call. Needed so far:

- Hero action shot — goalie mid-save, portrait/square orientation, high-res
- Coach portrait — square, on-field or clean headshot
- Coach's real name and finalized bio details (currently generic "the coach"
  copy pending a name)
- Business phone number (email is placeholder in `lib/site-config.ts`)
